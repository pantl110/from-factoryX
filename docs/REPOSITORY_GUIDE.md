## 2. 저장소 기본 정보

### 2.1 저장소가 두 개 있다 (가장 먼저 알아야 할 사실)

판틀110 코드는 **GitHub 저장소 두 곳**에 나뉘어 있다. 브랜치 이름이 서로 겹치기 때문에, 어느 저장소의 어느 브랜치인지 항상 함께 말해야 한다.

| 저장소 | 용도 (확인된 사실) | 확인된 상태 |
| --- | --- | --- |
| `pantl110/from-factoryX` | 백엔드·프론트엔드 주 개발과 PARTNER API 작업이 진행되는 저장소 | 백엔드·프론트엔드 최신 커밋이 여기에 있다 |
| `pantl110/from-factoryX-workex` | 일경험 인턴이 번역(다국어) 작업을 별도로 진행한 저장소 | `from-factoryX`를 복제한 뒤 **일부 브랜치만** 갈라졌다. **번역 작업은 아직 어디에도 병합되지 않았다** |

두 저장소는 같은 조상 이력을 공유한다. 브랜치별로 상태가 다르므로 아래 표로 확인한다(2026-09-09 기준).

| 브랜치 | 두 저장소 관계 |
| --- | --- |
| `dev`, `backend`, `frontend`, `frontend-v2-css-v1` | **같은 커밋을 가리킨다** (차이 없음) |
| `main` | `workex`가 **1커밋 앞서 있다** (`57537dd5` node_modules 추적 중단) |
| `backend-v2` | `workex`가 **17커밋 뒤처져 있다** (2026-03-19 시점 코드) |
| `frontend-v2` | `workex`가 **35커밋 뒤처져 있다** (2026-03-17 시점 코드) |
| `i18n-vi-id-ne-locales` | **`workex`에만 있다.** 이 브랜치의 출발점(`workex`의 `frontend-v2`)까지는 `from-factoryX`에도 있지만, 그 위에 쌓인 **번역 작업 커밋 9개는 `from-factoryX`에 없다** |

- 번역 브랜치는 **어느 브랜치에도 병합되지 않았다.** `workex`의 `main`에도 반영되어 있지 않다.
- 브랜치별로 앞선 쪽이 다르므로, "workex가 전부 옛 코드"라고 뭉뚱그려 판단하지 않는다.

**따라서 번역 작업을 반영하는 일은 "브랜치 병합"이 아니라 "저장소 간 이관"이다.** 일반 PR로 처리할 수 없으므로 8.4를 따른다.

> ⚠️ 번역 작업은 담당했던 일경험 인턴의 개인 작업물로 별도 저장소에만 남아 있고, 마지막 커밋 이후 시간이 지난 상태다. **인수 담당자가 정해지기 전까지 `workex` 저장소와 그 브랜치를 삭제하지 않는다.** 이 저장소가 정리되면 아직 반영되지 않은 작업이 그대로 사라진다.

> 이 저장소 두 개의 관계와 `workex`를 계속 유지할지는 아직 확정되지 않았다(15장). 확정 전에는 `workex`를 "아직 병합되지 않은 번역 작업이 들어 있는 별도 사본"으로만 취급하고, 여기에 새 기능 개발을 시작하지 않는다.

### 2.2 코드 구조

- 주 저장소: `https://github.com/pantl110/from-factoryX.git`
- 번역 작업 저장소: `https://github.com/pantl110/from-factoryX-workex.git`
- 하나의 저장소에 프론트엔드와 백엔드가 함께 들어 있다(모노레포). 모든 브랜치가 아래 골격을 공통으로 가진다.

```text
from-factoryX/
├── backend/            Django 백엔드 API
├── frontend/           Next.js 프론트엔드
├── nginx/              Nginx 설정
├── docker-compose.yml  로컬 컨테이너 구성
├── Makefile            개발 편의 명령어

```

> 위 골격은 공통이지만 **최상위 구성이 브랜치마다 완전히 같지는 않다.** 예를 들어 `backend-v2`에는 최상위 `migrations/` 폴더가 있고 다른 브랜치에는 없다. 파일이 있는지 없는지는 브랜치를 지정해서 직접 확인한다(6.1).
>
> 이 문서가 들어 있는 `docs/` 폴더는 2026-09-09 기준 **아직 어느 브랜치에도 커밋되지 않았다.** 커밋 전까지는 작성자 로컬에만 존재한다.

> 브랜치 이름이 `backend-...`, `frontend-...`이어도 그 브랜치에 백엔드나 프론트엔드 코드만 들어 있는 것이 아니다. 모든 브랜치에 전체 코드가 들어 있고, 이름은 "그 브랜치에서 주로 어떤 작업을 했는지"를 나타낼 뿐이다.

### 2.3 현재 저장소에 갖춰진 것과 없는 것

확인된 사실(2026-09-09 기준)이다. 없는 것을 있다고 가정하고 작업하지 않는다.

| 항목 | 상태 |
| --- | --- |
| PR 템플릿 (`.github/PULL_REQUEST_TEMPLATE.md`) | 있음. `CON-태스크번호` 형식으로 이슈를 연결하게 되어 있다 |
| GitHub Actions 등 자동 테스트·검사 | **없음.** PR을 올려도 자동으로 테스트가 돌지 않는다 |
| CODEOWNERS (자동 리뷰어 지정) | **없음** |
| 브랜치 보호 규칙 | 미확인 (15장 참고) |

**자동 검사가 없다는 뜻은, 코드가 동작하는지 확인하는 책임이 전부 사람에게 있다는 뜻이다.** PR을 올리는 사람이 어떤 테스트를 어떻게 실행했고 결과가 무엇이었는지 직접 적어야 한다.

### 2.4 로컬 폴더와 저장소를 혼동하지 않는다

내 컴퓨터에 있는 폴더가 곧 저장소는 아니다. 폴더 이름이 비슷해도 성격이 다르므로, 코드를 확인할 때는 **그 폴더가 무엇인지 먼저 확인한다.**

| 폴더 종류 | 성격 | 확인 방법 |
| --- | --- | --- |
| Git 클론 | 원격 저장소와 연결됨. 브랜치 이동·커밋·Push 가능 | `git remote -v`에 주소가 나온다 |
| 압축 파일로 받은 사본 | 특정 브랜치의 한 시점 스냅샷. **이력이 없어 커밋·Push 불가** | `.git` 폴더가 없다. 폴더 이름이 `-main` 등으로 끝나는 경우가 많다 |

압축 사본에서 코드를 수정하면 Git 이력에 남지 않고, 어느 시점 기준인지도 알 수 없게 된다. **개발은 반드시 클론에서 한다.** 압축 사본은 읽기·비교용으로만 쓴다.

내 폴더가 어떤 상태인지 확인하는 명령이다.

```bash
git remote -v            # 연결된 원격 저장소 (아무것도 안 나오면 클론이 아니다)
git branch --show-current # 현재 브랜치
git log -1               # 마지막 커밋
git status               # 커밋되지 않은 변경
```

### 2.5 절대 Git에 올리지 않는 것

- `.env` 파일, 실제 API Key·토큰·비밀번호·인증서
- 로컬 데이터베이스 파일, 가상환경(`.venv`), `node_modules`
- `__pycache__`, `*.pyc`, `.DS_Store`
- 개인 로컬 설정과 실행 산출물

실수로 비밀값을 커밋했다면 혼자 되돌리려 하지 말고 즉시 담당자에게 알린다. 이미 Push된 비밀값은 커밋을 지워도 유출된 것으로 취급하고 키를 폐기·재발급해야 한다.

> **현재 상태 주의 (2026-09-09 확인):** 위 규칙과 달리 `node_modules`가 이미 커밋되어 있는 브랜치가 있다. `main`, `dev`, `frontend`, `frontend-v2`에 176개 파일이 추적되고 있고, `backend`·`backend-v2`에는 없다. `workex`의 `main`에 하나 더 있는 커밋이 바로 이 추적을 중단한 `chore: stop tracking node_modules`다.
>
> 즉 **규칙과 현재 저장소 상태가 어긋나 있다.** 이미 추적되는 파일을 개인이 임의로 정리하지 않는다. 정리 여부·시점은 팀에서 결정한다(15장). 새로 추가하는 파일에는 위 규칙을 그대로 적용한다.

### 3.3 반드시 알고 있어야 하는 네 가지 주의점

**① `main`은 현재 최신 코드가 아니다.**
`main`만 보고 "이 기능은 구현되어 있지 않다"고 판단하면 틀린다. 기능이 다른 브랜치에만 있는 경우가 실제로 있었다. 새 작업을 시작하기 전에 6.1의 전체 확인 절차를 반드시 거친다.

**② `backend-v2`와 `frontend-v2`도 서로 갈라져 있다.**
두 브랜치의 공통 조상은 2025-08-26이고, 그 이후 `backend-v2`에만 668커밋, `frontend-v2`에만 579커밋이 각각 쌓였다.

> 숫자 주의: 3.1 표의 "579커밋"은 `main`과 `backend-v2`의 차이이고, 여기의 "579커밋"은 `frontend-v2`에만 있는 커밋 수다. 우연히 값이 같을 뿐 서로 다른 사실이다.

두 브랜치가 실제로 얼마나 다른지 확인한 결과다.

- `frontend/` 폴더: 두 브랜치 사이에 **810개 파일이 다르다**
- `backend/` 폴더: 두 브랜치 사이에 **375개 파일이 다르다**

즉 **백엔드 최신과 프론트엔드 최신이 동시에 들어 있는 브랜치는 현재 존재하지 않는다.** 프론트엔드와 백엔드를 함께 확인해야 하는 작업은 어느 한 브랜치만으로 검증할 수 없다는 뜻이므로, 시작 전에 담당자와 기준을 정해야 한다.

**③ 같은 이름의 브랜치가 두 저장소에 각각 있다.**
`backend-v2`, `frontend-v2`, `main`은 두 저장소에 모두 있지만 가리키는 코드가 다르다. (`dev`, `backend`, `frontend`, `frontend-v2-css-v1`은 양쪽이 같은 커밋이다 — 2.1) 어느 쪽인지에 따라 코드가 달라질 수 있으므로, 브랜치를 말할 때는 항상 저장소를 함께 적는다.

```text
잘못된 표현: "frontend-v2에 반영했습니다"
올바른 표현: "from-factoryX의 frontend-v2에 반영했습니다"
```

**④ 이름이 비슷해도 같은 개념이 아니다.**
- API 주소의 `/v2/...`는 **API 버전**이다.
- `backend-v2`, `frontend-v2`는 **Git 브랜치 이름**이다.
- 브랜치 이름의 `v2`가 API `v2`를 의미한다고 단정하지 않는다.

또한 병합 커밋 메시지에 `Merge pull request #NNN from Kr-TeamWise/...` 형태가 나온다. 이 `Kr-TeamWise` 조직과 현재 저장소의 관계(이전 저장소인지, 별도 조직인지, 권한이 어떻게 연결되는지)는 **미확인이다.** 추정하지 말고 확인한 뒤 이 문서에 기록한다(15장).

### 3.4 브랜치 이름만으로 판단하지 않는다

다음은 확인 없이 단정하면 안 되는 것들이다.

- 이름에 `v2`, `latest`, `final`이 있어도 최신이 아닐 수 있다
- 최근 커밋이 있어도 검토·승인이 끝난 코드가 아닐 수 있다
- 오래된 브랜치라도 아직 병합되지 않은 필요한 기능이 남아 있을 수 있다

판단은 항상 `git log`, 커밋 날짜, 병합 여부, 담당자 확인으로 한다.

## 4. 브랜치 종류와 역할

앞으로의 작업은 브랜치를 아래 세 종류로 구분해서 운영한다.

### 4.1 통합 브랜치 (장기 유지)

여러 사람의 작업이 모이는, 오래 유지되는 브랜치다. 통합 브랜치는 **개인이 임의로 만들지 않는다.** 새로 만들거나 역할을 바꿀 때는 팀 합의가 필요하고, 아래 항목에 답이 있어야 한다.

- 왜 이 브랜치가 필요한가
- 지금 개발의 공식 기준인가
- 어떤 작업이 이 브랜치로 PR을 보내는가
- 언제 어떤 방법으로 상위 브랜치(`main` 등)에 반영하는가
- 병합 책임자와 검증 책임자는 누구인가
- 이 브랜치를 언제 종료하는가

기록 위치는 다음과 같이 나눈다.

- **결정 내용과 승인자** → 14장 결정 기록에 한 줄 남긴다.
- **브랜치 목록과 현재 상태** → 3.1(또는 3.2) 표의 "확인된 상태" 칸을 갱신한다.

`main`과 오래 분리된 브랜치는 시간이 지날수록 합치기 어려워진다. 위 항목이 비어 있는 장기 브랜치는 관리되지 않는 브랜치로 본다.

### 4.2 작업 브랜치 (단기)

하나의 기능·수정을 위한 브랜치다. **모든 개발은 작업 브랜치에서 한다.**

- 목적은 하나만 갖는다. 하나의 브랜치에서 여러 기능을 섞지 않는다.
- 반드시 기준 브랜치와 PR 대상 브랜치를 정한 뒤에 만든다.
- 작업이 끝나고 PR이 병합되면 유지할 이유가 있는지 확인한다(12장).

### 4.3 통합 검증 브랜치 (임시)

서로 다른 작업을 공용 브랜치에 넣기 전에, 함께 동작하는지 확인하기 위해 임시로 만드는 브랜치다. 사용법은 10장에 있다.

## 5. 브랜치 이름 규칙

### 5.1 권장 형식

```text
<종류>/<대상-또는-기능>[-담당자]

feature/partner-api-security     새 기능
feature/user-language-setting    새 기능
fix/project-date-handling        오류 수정
hotfix/login-500                 운영 긴급 수정
integration/release-check        여러 작업 통합 검증
```

- 새 기능: `feature/<기능명>`
- 오류 수정: `fix/<오류명>`
- 운영 긴급 수정: `hotfix/<오류명>`
- 통합 검증: `integration/<목적>`

> 위 이름은 **형식을 보여주는 예시**이고, 실제로 존재하는 브랜치가 아니다. 지금 있는 브랜치는 3.1·3.2 표에서 확인한다. 예를 들어 번역 작업의 실제 브랜치 이름은 `feature/translation`이 아니라 `workex`의 `i18n-vi-id-ne-locales`다.

### 5.2 이름 규칙에 대한 현재 상태

과거 PR 이력에는 `Kr-TeamWise/backend-v2-june`, `Kr-TeamWise/backend-june-producthistory`처럼 **`<영역>-<담당자>-<작업>` 형식**으로 작업한 흔적이 남아 있다. (이 브랜치들은 현재 두 저장소의 브랜치 목록에는 없고, 병합 커밋 메시지에만 나온다.)

두 방식이 섞이면 브랜치 목록을 읽기 어려워지므로, 팀에서 한 가지를 선택해 14장에 결정 기록을 남긴다. 확정 전에는 **기존 이름을 임의로 바꾸지 않는다.**

### 5.3 이름 지을 때 지키는 것

- 사람이 읽고 목적을 알 수 있게 쓴다. `test`, `temp`, `new`, `작업중` 같은 이름은 쓰지 않는다.
- 만들기 전에 같은 목적의 브랜치·PR이 이미 있는지 검색한다.
- 이름에 상태(`done`, `final`)를 넣지 않는다. 상태는 13장 등록표에서 관리한다.

## 6. 새 작업을 시작하는 절차

### 6.1 1단계 — 저장소 전체를 확인한다

현재 열려 있는 폴더와 `main`만 보고 판단하지 않는다.

```bash
git fetch --prune origin          # 원격 브랜치 목록 최신화
git branch -a                     # 로컬·원격 전체 브랜치 확인
git status                        # 커밋되지 않은 변경 확인
git branch --show-current         # 지금 어느 브랜치인지 확인
git log --oneline --decorate -10  # 최근 이력 확인
```

브랜치를 이동하지 않고도 다른 브랜치의 내용을 확인할 수 있다.

```bash
git ls-tree -r --name-only origin/<브랜치명>            # 그 브랜치의 파일 목록
git show origin/<브랜치명>:<파일경로>                   # 그 브랜치의 파일 내용
git rev-list --left-right --count origin/A...origin/B  # 두 브랜치가 얼마나 갈라졌는지
git log --all --oneline --grep="<검색어>"               # 전체 브랜치에서 관련 커밋 검색
```

> 갈라진 커밋 수를 셀 때는 `git rev-list`를 쓴다. `git log`에는 `--count`가 없어서 개수 대신 커밋 로그 전체가 출력된다(오류도 나지 않으므로 잘못 쓴 것을 알아채기 어렵다).
> 출력은 `<왼쪽만 있는 커밋 수>  <오른쪽만 있는 커밋 수>` 두 숫자다. 예를 들어 `0  579`는 왼쪽 브랜치에만 있는 커밋이 없고, 오른쪽 브랜치에만 579개가 있다는 뜻이다.

다음을 함께 확인한다. **2번과 6번을 건너뛰면 9.4처럼 같은 기능을 두 번 만들게 된다.**

1. GitHub의 전체 브랜치 목록과 열려 있는 PR
2. **내가 만들려는 기능이 다른 브랜치에 이미 있는지**
3. 관련 파일·라우터·모델·마이그레이션의 위치
4. 각 브랜치의 최근 커밋일과 담당자
5. 내 작업이 프론트엔드와 백엔드 중 어디를 건드리는지, 그 두 최신 코드가 지금 어느 브랜치에 있는지
6. **다른 저장소(`from-factoryX-workex`)에 같은 기능이나 관련 작업이 있는지** (2.1)
7. **같은 목적의 브랜치가 이미 있는지, 있다면 새로 만들지 말고 정리 후 재사용할지** — 이름만 다른 중복 브랜치가 생기면 어느 것이 최신인지 알 수 없게 된다. 기존 브랜치가 있으면 담당자에게 상태를 확인하고, 이어서 쓸지·정리하고 새로 만들지 결정한 뒤 시작한다.

기능 이름·필드 이름으로 두 저장소를 함께 검색한다.

```bash
git log --all --oneline --grep="<기능 키워드>"       # 관련 커밋 검색
git log --all --oneline -- "<관련 파일 경로>"        # 그 파일을 건드린 브랜치 찾기
git grep -l "<필드명·함수명>" origin/<브랜치명>      # 그 브랜치에 이미 있는지 확인
```

### 6.2 2단계 — 기준을 확정한다

**아래 다섯 가지에 답할 수 없으면 코드를 수정하지 않는다.**

1. 이 작업의 최신 기준 코드는 어느 브랜치인가
2. PR은 어느 브랜치로 보내는가
3. 지금 진행 중인 다른 작업과 같은 파일을 건드리는가
4. 데이터베이스 모델·마이그레이션이 바뀌는가
5. 운영 배포는 누가 언제 승인하는가

모르는 항목은 추정하지 않고 담당자에게 확인한다. 확인이 끝나기 전까지는 **읽기(조사)만** 한다.

### 6.3 3단계 — 작업을 등록한다

13장 등록표에 작업을 추가한다. 확인되지 않은 값은 비워두지 않고 `미확인`으로 적는다.

### 6.4 4단계 — 브랜치를 만든다

```bash
git fetch origin
git switch -c feature/<기능명> origin/<기준브랜치>
```

작업 시작 시점의 기준 커밋을 기록해 둔다. 나중에 "이 작업이 무엇을 기준으로 시작됐는지" 확인할 수 있어야 한다.

```bash
git rev-parse --short HEAD
```

## 7. 개발 중 관리

### 7.1 커밋 규칙

최근 작업은 아래 형식(Conventional Commits)을 쓰고 있다. 계속 이 형식을 따른다. (`main`의 오래된 커밋에는 `설비 수정`처럼 형식 없는 한국어 메시지도 섞여 있다. 과거 이력을 고치지는 않는다.)

```text
<종류>(<범위>): <내용>

feat(profit): add profit detail endpoint
fix(cors): strip trailing slash from CORS_ALLOWED_ORIGINS
refactor(stock): streamline material creation
chore(gitignore): add migration log files
```

- `feat` 기능 추가 / `fix` 오류 수정 / `refactor` 동작 변화 없는 구조 개선 / `chore` 설정·빌드·문서 등 부수 작업
- **한 커밋에는 설명할 수 있는 하나의 변경만 담는다.** 나중에 문제가 생겼을 때 필요한 커밋만 되돌리거나 옮길 수 있어야 한다.

### 7.2 작업 중 지키는 것

1. 작업 중 다른 기능의 문제를 발견하면 현재 브랜치에 임의로 포함하지 않는다.
   - 현재 작업에 반드시 필요한 수정이면, 사유와 승인받은 사실을 기록하고 포함한다.
   - 별개 문제라면 새 작업으로 분리한다.
2. 코드와 테스트를 함께 수정한다. 테스트가 실패할 때 기대값만 바꾸는 것은 실제 서비스 규칙과 일치하는지 확인한 경우에만 한다.
3. 커밋 전에 변경 목록을 눈으로 확인한다. 비밀값·로컬 파일이 섞이지 않았는지 매번 확인한다.
   ```bash
   git status
   git diff --staged
   ```
4. 같은 파일을 다른 사람이 수정하고 있다면, 병합 전에 변경 의도를 서로 공유한다.
5. 진행 내용·테스트 결과·발견한 위험·다음 할 일을 작업일지에 기록한다.

## 8. PR·리뷰·병합·배포 절차

### 8.1 전체 흐름

```text
요구사항·담당자 확인
        ↓
기준 브랜치 확인 및 작업 등록 (6장)
        ↓
작업 브랜치에서 개발 → 테스트 → Push
        ↓
PR 생성 (PR 템플릿 + 8.2 항목 작성)
        ↓
코드 리뷰 · 충돌 확인 · 테스트 결과 확인
        ↓
승인 후 대상 브랜치에 병합
        ↓
통합 환경 검증
        ↓
별도 배포 승인
        ↓
운영 배포 · 확인 · 기록
```

**병합과 배포는 다른 작업이다.** PR이 병합됐다는 사실을 "배포 완료"로 기록하지 않는다.

### 8.1.1 병합 시점 원칙 — 이벤트 기준 + 주 1회 점검

병합 시점은 아래 두 가지를 함께 운영한다. 하나만 하면 기준 브랜치가 다시 벌어진다.

**① 개별 병합은 "리뷰 승인 시점"에 한다 (이벤트 기준).**
정해진 날짜를 기다리지 않는다. 리뷰와 검증이 끝난 PR은 그때 병합한다. 승인된 작업을 모아두면 서로 충돌이 커지고, 누가 무엇을 기다리는지 알 수 없게 된다.

**② 그와 별개로 주 1회 통합 점검을 한다 (주기 기준).**
개별 병합만으로는 오래 유지되는 브랜치끼리 벌어지는 것을 막을 수 없다. 매주 정해진 시점에 아래를 확인하고 결과를 기록한다.

- 기준 브랜치들 사이의 차이 (`git rev-list --left-right --count`)
- 30일 이상 커밋이 없고 병합되지 않은 브랜치
- 승인됐는데 아직 병합되지 않은 PR
- 13.2 등록표의 상태가 실제와 맞는지

> 이 저장소는 `main`이 1년 넘게 멈춘 채 `backend-v2`가 579커밋, `frontend-v2`가 별도로 벌어진 상태까지 왔다(3장). 주기 점검이 없으면 같은 일이 반복된다. 점검 주기와 담당자는 팀에서 확정한다(15장).

### 8.2 PR에 반드시 적는 것

저장소 PR 템플릿에 더해 다음을 적는다. 자동 테스트가 없으므로 이 정보가 리뷰의 유일한 근거다.

- 작업 목적과 요구사항 근거(기획서·문서·승인 메시지 위치)
- 기준 브랜치와 PR 대상 브랜치
- 주요 변경 파일과 동작이 어떻게 달라지는지
- 모델·마이그레이션·환경 변수·외부 서비스 변경 여부
- **실행한 테스트와 결과** (자동/수동 각각, 실패한 항목 포함)
- **실행하지 못한 테스트와 그 이유**
- 다른 진행 중 작업과의 의존·충돌 여부
- 배포 전 추가로 확인해야 할 사항

### 8.3 리뷰와 병합 권한

- 자기 PR을 스스로 승인·병합하지 않는다.
- 병합은 대상 브랜치의 책임자 또는 지정된 리뷰어 승인 후에 한다.
- 필수 리뷰어 수와 병합 권한자는 아직 확정되지 않았다(15장). **확정 전에는 대상 브랜치 주 작업자와 기술 책임자의 확인을 받고 병합한다.**

### 8.4 다른 저장소의 작업을 가져올 때

`from-factoryX`와 `from-factoryX-workex`처럼 저장소가 다르면 GitHub PR을 바로 만들 수 없다. 아래 순서로 진행하고, **시작 전에 양쪽 담당자와 기술 책임자의 승인을 받는다.**

1. **목적지를 먼저 정한다.** 가져올 작업이 최종적으로 어느 저장소의 어느 브랜치에 들어가야 하는지, 그 작업의 책임자가 누구인지 정한다.
2. **기준 차이를 확인한다.** 그 작업이 어느 시점 코드를 기준으로 만들어졌는지, 목적지가 그보다 얼마나 앞서 있는지 확인한다. 차이가 크면 그대로 합치지 않는다.
3. **같은 기능이 목적지에 이미 있는지 확인한다.** 저장소가 나뉘면 같은 기능을 서로 모르게 두 번 만들 수 있다. 9.4의 실제 사례를 반드시 읽는다.
4. **이력이 남는 방법으로 가져온다.** 상대 저장소를 임시 원격으로 추가해 이력을 가져오거나, 변경을 패치로 옮긴다. **파일을 복사해 덮어쓰는 방식은 작성자와 이력이 사라지므로 쓰지 않는다.**
5. **통합 검증 브랜치에서 먼저 확인한다.** 목적지 기준으로 `integration/...`을 만들어 합친 뒤 동작을 확인하고, 그 결과로 PR을 만든다.
6. **결과를 기록한다.** 무엇을 어디에서 어디로 옮겼는지 13장·14장에 남긴다.

원격 추가는 저장소 설정을 바꾸는 작업이므로 임의로 하지 않고 담당자 확인 후 진행한다.

## 9. 브랜치를 합치기 전 점검

브랜치 병합은 파일을 복사하는 작업이 아니라, **두 갈래의 변경 이력과 기능이 함께 동작하도록 만드는 작업**이다. 특히 오래 갈라져 있던 브랜치는 충돌 없이 합쳐져도 동작이 깨질 수 있다.

### 9.1 공통 체크리스트

- [ ] 원본 브랜치와 대상 브랜치가 정확하다
- [ ] 양쪽 담당자에게 병합 목적과 시점을 확인했다
- [ ] 양쪽에 커밋되지 않은 변경이 없다 (`git status`)
- [ ] 두 브랜치가 얼마나 갈라졌는지 확인했다 (`git rev-list --left-right --count A...B`)
- [ ] 같은 파일을 양쪽에서 수정한 목록을 확인했다
- [ ] 삭제·이름 변경된 파일을 확인했다
- [ ] 병합 후 실행할 테스트 목록을 정했다
- [ ] 실패했을 때 원래 상태로 되돌릴 방법이 있다 (병합 전 커밋 해시 기록, 브랜치 보존)

겹치는 파일을 확인하는 명령이다.

```bash
git fetch origin
git diff --name-only origin/<대상브랜치>...<내브랜치>   # 내가 바꾼 파일
git diff --name-status origin/<대상브랜치>...<내브랜치> # 추가·수정·삭제 구분
git merge-base origin/<대상브랜치> <내브랜치>           # 공통 조상 확인
```

### 9.2 특별히 위험한 변경 (반드시 개별 확인)

| 항목 | 확인 내용 |
| --- | --- |
| 마이그레이션 | 마이그레이션 번호가 중복되거나 의존 관계가 어긋나지 않는지. 양쪽이 같은 모델을 바꿨는지 |
| 모델·데이터베이스 | 필드 삭제·형 변경이 기존 데이터와 충돌하지 않는지 |
| URL·라우터 등록 | 같은 경로가 중복 등록되거나, 병합 과정에서 누락되지 않았는지 |
| 인증·권한·미들웨어 | 권한이 의도보다 넓어지거나 우회되지 않는지 |
| 설정·의존성 파일 | 환경 변수, `requirements.txt`, `package.json`이 한쪽 것만 남지 않았는지 |
| 공통 유틸리티·스키마 | 양쪽이 같은 함수를 다르게 바꾸지 않았는지 |
| 배포 설정 | Docker·nginx·Railway 설정이 뒤섞이지 않았는지 |

**기존 마이그레이션 파일은 임의로 수정·삭제하지 않는다.** 문제가 있으면 담당자와 함께 처리한다.

### 9.3 병합 방식

방식은 담당자 확인과 충돌 점검 후에 정한다. 혼자 판단하지 않는다.

| 방식 | 설명 | 주의 |
| --- | --- | --- |
| `merge` | 양쪽 이력을 유지하며 합친다 | 기본 선택. 이력이 남아 추적하기 쉽다 |
| `rebase` | 내 작업의 시작 기준을 새 기준 위로 옮긴다 | 이미 다른 사람과 공유한 브랜치에서는 이력이 바뀌므로 주의 |
| `cherry-pick` | 필요한 커밋만 골라 옮긴다 | 앞뒤 의존 커밋이 빠질 수 있어 전체 의존성을 확인해야 한다 |

**원격에 Push된 공동 브랜치에 승인 없이 force push 하지 않는다.**

방식 선택에 참고할 기준이다.

| 상황 | 권장 |
| --- | --- |
| 내 브랜치를 이미 원격에 Push했다 | `merge`. `rebase`는 이력이 바뀌어 원격과 어긋나고 force push가 필요해진다 |
| 충돌이 여러 파일에 걸쳐 있다 | `merge`. `rebase`는 커밋마다 같은 충돌을 반복 해결해야 한다 |
| 아직 Push하지 않은 커밋 1~2개다 | `rebase`도 가능. 이력이 깔끔해진다 |
| 대상 브랜치의 특정 수정 하나만 필요하다 | `cherry-pick`. 단, 의존 커밋을 함께 확인한다 |

실제로 병합하기 전에 9.5.2의 사전 검사로 충돌 규모를 먼저 확인한 뒤 방식을 정한다.

### 9.4 실제 사례 ① 같은 기능이 두 번 만들어진 경우 (2026-09-09 확인)

이 사례는 이 문서의 규칙이 왜 필요한지 보여주는 실제 예시다. 앞으로 병합을 준비할 때 같은 방식으로 점검한다.

사용자 언어 설정(`user.language`) 기능이 **두 저장소에서 각각 따로 만들어졌다.**

| 항목 | `from-factoryX`의 `backend-v2` | `workex`의 `i18n-vi-id-ne-locales` |
| --- | --- | --- |
| 마이그레이션 파일 | `user/0006_user_language.py` | `user/0003_user_language.py` |
| 앞선 마이그레이션 | `0005_...` | `0002_...` |
| 선택 가능 언어 | 한국어, 영어 | 한국어, 영어, 베트남어, 인도네시아어, 네팔어 |
| 필드 길이 | `max_length=10` | `max_length=2` |
| 생성 시점 | 2025-12-31 | 2026-07-01 |

그대로 합치면 다음 문제가 발생한다.

1. **마이그레이션 번호 충돌** — 목적지에는 이미 `0003_alter_user_status.py`가 있으므로 `0003_user_language.py`와 번호가 겹친다. Django는 같은 앱에 갈라진 마이그레이션이 둘 있으면 실행을 거부한다.
2. **같은 필드를 두 번 추가** — 두 마이그레이션이 모두 `user.language` 필드를 추가하므로 순서대로 실행하면 오류가 난다.
3. **필드 정의 불일치** — `max_length`가 10과 2로 달라 데이터베이스 컬럼 정의가 어긋난다.

즉 이 작업은 **파일을 합치는 문제가 아니라, 어느 정의를 최종안으로 삼을지 결정해야 하는 문제**다. 결정 없이 병합을 시도하면 안 된다. 이런 경우의 처리 순서는 다음과 같다.

1. 두 작업의 담당자와 기술 책임자가 최종 필드 정의를 결정한다(지원 언어 목록, 필드 길이).
2. 목적지 브랜치의 마이그레이션 번호 다음 번호로 **새 마이그레이션을 하나만** 만든다.
3. 중복된 마이그레이션은 목적지에 가져오지 않는다.
4. 화면 번역 리소스(`frontend/src/messages/*.json` 등)와 백엔드 필드 정의가 서로 맞는지 확인한다.
5. 결정 내용을 14장에 기록한다.

**교훈:** 새 작업을 시작하기 전 6.1의 전체 확인 절차(다른 브랜치·다른 저장소에 같은 기능이 있는지)를 건너뛰면, 나중에 합치는 비용이 개발 비용보다 커진다.

### 9.5 충돌이 났을 때 해결하는 방법

병합을 실행하면 Git이 자동으로 합칠 수 없는 파일에 충돌 표시를 남긴다. 여기서 무엇을 기준으로 판단해야 하는지 정리한다.

#### 9.5.1 먼저 알아야 할 원칙

**① 충돌 해결은 "어느 쪽을 고르는 작업"이 아니다.**
양쪽 변경의 *의도를 모두 살리는 코드를 만드는 작업*이다. 한쪽을 통째로 선택하면 다른 쪽 작업이 조용히 사라진다. 테스트가 통과해도 사라진 기능은 드러나지 않는다.

**② 대상 브랜치(공용 브랜치)의 구조를 기준으로 삼고, 내 변경을 그 구조에 다시 얹는다.**
대상 브랜치는 여러 사람이 쓰는 코드다. 내 파일로 덮으면 그 사이 다른 사람이 한 작업이 되돌아간다.

**③ 판단이 안 되면 그 파일을 마지막에 수정한 사람에게 확인한다.**
추측해서 지우지 않는다. 확인하는 시간이 되돌리는 시간보다 항상 짧다.

#### 9.5.2 충돌을 미리 확인하는 방법 (권장)

실제로 병합하기 전에, **브랜치와 작업 트리를 건드리지 않고** 충돌 여부만 미리 볼 수 있다.

```bash
git fetch origin
git merge-tree --write-tree --name-only origin/<대상브랜치> <내브랜치>
```

- 출력에 `CONFLICT (content): Merge conflict in <파일>`로 충돌 파일이 나열된다.
- `Auto-merging <파일>`만 있고 `CONFLICT`가 없는 파일은 자동으로 합쳐진다.
- 이 명령은 아무것도 바꾸지 않으므로, 병합 계획을 세우거나 담당자에게 보고할 때 먼저 실행한다.

#### 9.5.3 해결 절차

1. **통합 검증 브랜치에서 시작한다.** 대상 브랜치 기준으로 `integration/...`을 만들고 거기서 병합한다. 내 원래 작업 브랜치는 그대로 보존한다.
   ```bash
   git switch -c integration/<목적> origin/<대상브랜치>
   git merge <내브랜치>
   ```
2. **충돌 파일 목록을 확보한다.**
   ```bash
   git status --short | grep '^UU'   # 양쪽이 수정해 충돌한 파일
   git diff --name-only --diff-filter=U
   ```
3. **파일 하나마다 세 가지 버전을 읽는다.** 충돌 표시만 보고 고치지 말고, 각각이 원래 무엇이었는지 확인한다.
   ```bash
   git show :1:<파일경로>   # 공통 조상 (갈라지기 전 원본)
   git show :2:<파일경로>   # 대상 브랜치 쪽 내용
   git show :3:<파일경로>   # 내 브랜치 쪽 내용
   ```
   이 세 명령은 **병합이 진행 중인 상태(충돌이 남아 있는 동안)에만** 동작한다. 병합을 끝내거나 중단하면 쓸 수 없다.
4. **양쪽 변경의 의도를 각각 한 줄로 적는다.** 예: "대상 브랜치: 에러 처리를 공통 유틸로 교체 / 내 작업: 조회 조건에 `factory_id` 추가". 이 한 줄이 정리되지 않으면 아직 고칠 준비가 안 된 것이다.
5. **두 의도를 모두 만족하는 코드로 다시 쓴다.** 충돌 표시(`<<<<<<<`, `=======`, `>>>>>>>`)는 모두 지운다.
6. **해결 내용을 기록한다.** 파일별로 "무엇과 무엇을 어떻게 합쳤는지"를 작업일지에 남긴다. PR 설명에도 그대로 쓴다.
7. **검증한다.** 자동 테스트 전체 실행 + 내 기능이 실제로 동작하는지 직접 호출해 확인한다. **자동 테스트 통과만으로 "내 작업이 살아 있다"고 판단하지 않는다.** 권한 제한·인증처럼 테스트에 없는 동작은 직접 확인해야 한다.

#### 9.5.4 하면 안 되는 것

- 충돌 표시(`<<<<<<<`)가 남은 채로 커밋
- 내용을 확인하지 않고 `git checkout --ours` / `--theirs`로 파일 전체를 한쪽으로 덮기
- 테스트가 깨진 상태에서 테스트 기대값만 바꿔 통과시키기
- 해결이 어려워서 `git reset --hard`로 되돌리기 (작업이 사라진다)
- 충돌이 많다고 파일을 직접 복사해 붙여넣기 (이력과 작성자가 사라진다)

#### 9.5.5 막혔을 때

혼자 판단하지 않고 멈춘다. 아래를 정리해서 담당자에게 확인한다. 정리만 해도 대부분 판단이 쉬워진다.

- 어느 파일이 충돌했는지
- 대상 브랜치 쪽은 무엇을 왜 바꿨는지 (`git log origin/<대상브랜치> -- <파일>`로 확인)
- 내 쪽은 무엇을 왜 바꿨는지
- 내가 판단하기 어려운 지점이 정확히 무엇인지

### 9.6 실제 사례 ② 같은 파일을 양쪽이 각각 고친 경우 (2026-09-09 확인)

9.4가 "같은 기능을 두 번 만든" 경우라면, 이 사례는 **"내 작업과 대상 브랜치가 같은 파일을 각자 고친"** 경우다. 앞으로 가장 자주 마주칠 유형이다.

**상황** — PARTNER API 보안 작업을 `main` 기준으로 시작했는데, 작업 중 일부 PARTNER API의 라우터·조회 처리 코드가 `main`에 없다는 것을 발견했다. 확인해보니 그 코드는 `backend-v2`에 있었다. 즉 작업의 기준이 처음부터 최신 코드가 아니었다.

**확인된 사실** (`git merge-tree` 사전 검사 결과)

| 구분 | 파일 수 | 내용 |
| --- | --- | --- |
| 두 갈래의 공통 기준점 | — | `main` 팁과 정확히 일치. 작업이 유실될 구조적 위험은 없다 |
| 내 작업이 바꾼 파일 (전체) | 34개 | 아래 세 가지로 나뉜다 |
| 충돌 없이 추가되는 신규 파일 | 12개 | API Key 앱, Rate Limit 등 대상 브랜치에 없던 파일 |
| 자동으로 합쳐지는 파일 | 6개 | 양쪽이 서로 다른 위치를 고쳤거나, 한쪽만 고친 파일 |
| **충돌하는 파일** | **16개** | 양쪽이 같은 위치를 고친 파일 |
| 대상 브랜치에만 있는 API 파일 | 14개 | 보안 작업이 아직 적용되지 않은 API들 (병합 후 추가 작업 대상) |

**충돌 원인** — 대상 브랜치에서 같은 파일들이 리팩터링(에러 처리·필드 관리 공통 유틸 도입)되어 있었다. 내 작업은 그 리팩터링 이전 구조 위에 조회 조건을 추가한 상태였다.

**따라서 이렇게 해결한다**

1. 내 파일로 덮지 않는다. 덮으면 대상 브랜치의 리팩터링이 사라진다.
2. 대상 브랜치의 새 구조를 유지하고, 그 구조에 내 변경(공장 범위 제한 조건)을 다시 얹는다.
3. 병합만으로 끝나지 않는다. **대상 브랜치에만 있던 API 14개에는 같은 보안 작업을 새로 적용해야 한다.** 병합 후 남는 작업 범위를 계획에 포함한다.
4. 자동 테스트 통과와 별개로, 권한 제한이 실제로 동작하는지 직접 호출해 확인한다.

**교훈:** 기준 브랜치를 잘못 잡으면 코드가 사라지지는 않지만, **합치는 작업과 다시 적용하는 작업이 추가로 생긴다.** 6.2의 "기준 확정" 단계를 작업 시작 전에 반드시 거친다.

## 10. 여러 기능이 동시에 진행될 때

### 10.1 기능 브랜치끼리 직접 합치지 않는다

```text
공식 기준 브랜치
├─ feature/A
├─ feature/B
└─ feature/C
```

- `feature/A`에 `feature/B`를 직접 병합하지 않는다. 두 작업의 완료 시점이 달라지면 어느 브랜치가 어디까지 포함하는지 추적할 수 없게 된다.
- 다른 사람 브랜치를 내 브랜치로 가져오기 전에 반드시 담당자 확인을 받는다.

### 10.2 함께 시험해야 할 때는 통합 검증 브랜치를 쓴다

```text
공식 기준 브랜치
└─ integration/<목적>
   ├─ 검토된 A 작업
   ├─ 검토된 B 작업
   └─ 검토된 C 작업
```

- 통합 브랜치는 **검증 목적의 임시 브랜치**다. 여기서 바로 배포하지 않는다.
- 통합 중 발견한 수정은 가능하면 원래 기능 브랜치에도 반영해서, 변경의 출처를 유지한다.
- 검증이 끝나면 각 기능은 원래 계획한 PR 경로로 대상 브랜치에 반영한다.
- 통합 브랜치는 목적을 달성하면 정리한다.

### 10.3 동시에 진행할 때 겹치기 쉬운 파일

새 작업을 시작할 때, 아래 파일들은 다른 작업과 겹치는지 먼저 확인한다.

- URL·라우터 등록 파일
- 설정 파일(`settings`, `.env` 예시, `docker-compose.yml`)과 의존성 파일
- 인증·권한·미들웨어
- 공통 모델과 마이그레이션
- 공통 스키마·유틸리티
- 같은 API 경로, 같은 화면 컴포넌트, 같은 번역·문자열 리소스
- 테스트와 배포 설정

## 11. 승인 없이 하면 안 되는 것

담당자·기술 책임자 승인 없이 다음을 하지 않는다.

- `main` 직접 커밋·Push
- 다른 사람의 브랜치를 병합·rebase·삭제
- 공유된 원격 브랜치에 force push
- `git reset --hard`, 대량 파일 삭제, 브랜치 삭제
- 기존 마이그레이션 파일 수정·삭제
- 운영 데이터베이스 직접 변경
- 운영 비밀키·토큰·실제 API Key를 코드·문서·채팅에 기록
- 테스트 실패를 감추기 위한 테스트 삭제·비활성화
- 문서에 없거나 승인받지 않은 기능·권한 추가
- PR 승인 없는 운영 배포
- 기존 브랜치의 역할 변경 또는 새 장기 브랜치 생성

**막혔을 때 되돌리기 어려운 명령으로 상황을 넘기지 않는다.** 원인을 확인하고, 판단이 어려우면 멈추고 물어본다.

## 12. 브랜치 정리 규칙

브랜치가 계속 쌓이면 어느 브랜치가 최신인지 아무도 알 수 없게 된다. 현재 두 저장소에 이름이 겹치는 장기 브랜치가 여러 개 있고, `main`에 반영되지 않은 브랜치도 남아 있다(3.1·3.2).

- 브랜치를 만들 때 담당자·목적·기준·PR 대상·상태를 13장에 등록한다.
- PR이 병합되면 그 브랜치를 계속 유지할 이유가 있는지 확인한다.
- 삭제는 담당자 확인 후에 한다. 이력은 병합 커밋·PR·태그로 남는다.
- 30일 이상 커밋이 없고 병합되지 않은 브랜치는 담당자에게 상태를 확인한다. (기간은 팀 합의로 조정)
- 장기 브랜치는 정기적으로 `main`과의 차이, 아직 반영되지 않은 기능, 종료 계획을 점검한다.
- 새 브랜치를 만들기 전에 같은 목적의 기존 브랜치·PR을 검색한다(6.1의 7번).

**주 1회 통합 점검을 고정 일정으로 운영한다.** 개별 병합은 리뷰 승인 시점에 하고(8.1.1), 그것과 별개로 매주 아래를 확인해 결과를 기록한다. 점검하지 않으면 브랜치는 반드시 다시 벌어진다.

| 점검 항목 | 확인 방법 |
| --- | --- |
| 기준 브랜치들 사이의 차이가 커지고 있는지 | `git rev-list --left-right --count origin/A...origin/B` |
| `main`에 반영되지 않은 브랜치 목록 | `git branch -r --no-merged origin/main` |
| 30일 이상 멈춘 미병합 브랜치 | 각 브랜치 최근 커밋일 확인 |
| 승인됐는데 병합 안 된 PR | GitHub PR 목록 |
| 13.2 등록표가 실제 상태와 맞는지 | 담당자별 확인 |

병합 여부를 확인하는 명령이다.

```bash
git branch -r --merged origin/main      # main에 이미 반영된 브랜치
git branch -r --no-merged origin/main   # main에 반영되지 않은 브랜치
```

### 12.1 단기·외주·인턴 작업물 관리

기간이 정해진 인력(일경험 인턴, 외주, 단기 참여자)의 작업은 **작업이 끝난 뒤 반영되지 못하고 남는 일이 실제로 발생한다.** 번역 작업이 그 사례다(2.1). 같은 일이 반복되지 않도록 아래 3단계를 지킨다. **세 단계 모두 작업자 본인이 아니라 작업을 맡기는 쪽이 챙겨야 한다.**

#### 1단계 — 착수 시 (작업 시작 전에 정해둔다)

- **주 저장소 안에 브랜치를 만든다.** 저장소를 새로 복제해서 작업하지 않는다. 별도 저장소에서 시작하면 나중에 병합이 아니라 저장소 간 이관 문제가 된다(8.4).
- **기준 브랜치를 주 개발 기준과 맞춘다.** 오래된 기준에서 시작하면 반영 비용이 커진다.
- **작업 종료 예정일을 13.2 등록표에 함께 적는다.**
- **검토·인수할 내부 담당자(검토자)를 미리 지정한다.** 작업자가 떠난 뒤에 인수자를 찾기 시작하면 늦다.

#### 2단계 — 종료 전 (작업자가 있는 동안 받아둔다)

- **작업 종료 전에 PR을 올려 검토를 시작한다.** "끝나고 나중에 합치기"로 미루지 않는다.
- **미완료 항목과 판단 근거를 문서로 남기게 한다.** 무엇을 왜 그렇게 정했는지, 검증한 범위와 못 한 범위를 적게 한다.
- **인수 담당자가 종료 전에 코드를 직접 실행해 확인한다.** 작업자가 떠난 뒤 물어볼 수 없는 질문이 남지 않게 한다.

#### 3단계 — 종료 후 (반영 결정까지 보존한다)

- **반영 또는 폐기 결정이 나기 전까지 브랜치·저장소를 삭제하지 않는다.**
- **반영하지 않기로 결정했다면 그 이유를 14장에 기록한다.** 결정 없이 방치하지 않는다.
- **계정 권한이 회수되어도 작업물이 남아 있는지 확인한다.** 개인 저장소에만 있는 작업은 조직 저장소로 옮긴다.

모든 신규 작업은 코드를 수정하기 전에 아래 정보를 정리한다. 확인되지 않은 값은 `미확인`으로 적는다.

- **13.2 요약표**에는 6개 열(작업명 / 담당자 / 저장소·작업 브랜치 / 기준 브랜치 / PR 대상 / 상태)만 적는다. 누가 어디서 무엇을 하고 있는지 한눈에 보는 것이 목적이다.

| **`user.language` 최종 필드 정의** (지원 언어 목록, 필드 길이) | 두 저장소에 서로 다른 정의가 있어 그대로 합칠 수 없다(9.4). 번역 작업 인수의 첫 단계다 | 결정 전에는 번역 작업 병합을 시작하지 않는다 |
| 번역 작업의 이관 목적지 브랜치 | 저장소 간 이관은 일반 PR로 되지 않는다(8.4) | 이관 방법·시점을 결정권자와 합의한 뒤 진행한다 |
| 번역 작업 인수인계 자료 유무 | 인턴 작업물이므로 판단 근거(지원 언어 결정 이유, 미완료 항목, 검증 범위)가 문서로 남아 있는지 확인해야 한다 | 브랜치 내 `docs/i18n-language-addition-guide.md`와 커밋 메시지를 먼저 확인한다 |
| **저장소를 하나로 통합할지, 두 개를 유지할지** | 같은 이름의 브랜치가 두 곳에 있어 어느 코드가 기준인지 알 수 없다. 같은 기능이 두 번 만들어진 사례가 이미 발생했다(9.4) | 새 개발은 `from-factoryX`에서만 시작한다 |
| `workex` 저장소의 역할과 종료 계획 | 미병합 번역 작업이 여기에만 있어 정리 없이 방치하면 작업이 유실될 수 있다 | 번역 작업을 옮기기 전까지 `workex` 저장소와 브랜치를 삭제하지 않는다 |
| 백엔드·프론트엔드 최신 코드를 하나로 합칠 계획과 담당자 | `backend-v2`와 `frontend-v2`가 서로 갈라져 있어 전체 동작을 검증할 브랜치가 없다(3.3②) | 프론트·백엔드 동시 검증이 필요한 작업은 시작 전 결정권자 확인 |
| `backend-v2`·`frontend-v2` → `main` 반영 시점과 책임자 | `main`이 1년 넘게 멈춰 있어 무엇이 공용 기준인지 불명확하다 | `main`은 직접 수정하지 않는다 |
| PR 필수 리뷰어 수와 병합 권한자 | 리뷰 없는 병합을 막는 최소 장치 | 대상 브랜치 주 작업자 + 기술 책임자 확인 후 병합 |
| 주 1회 통합 점검의 요일·담당자 | 8.1.1·12장에 주기 점검을 원칙으로 넣었으나 실행 주체가 없으면 지켜지지 않는다 | 담당자가 정해질 때까지 각 작업 담당자가 자기 브랜치 차이를 확인한다 |
| 브랜치 이름 규칙 통일안 (`feature/...` vs `<영역>-<담당자>-<작업>`) | 두 방식이 섞여 목록을 읽기 어렵다 | 새 브랜치는 5.1 형식을 쓰고, 기존 브랜치 이름은 바꾸지 않는다 |
| 상시 통합 브랜치 운영 여부 | 기능이 늘어날 때 통합 검증 위치가 필요하다 | 필요할 때만 `integration/...`을 임시로 만든다 |
| 운영 배포 담당자와 승인 절차 | 병합과 배포를 분리하기 위해 필요하다 | 배포는 승인 없이 하지 않는다 |
| 자동 테스트·검사 도입 여부 | 현재 PR에 자동 검사가 없어 검증이 사람에게만 의존한다 | PR에 실행한 테스트와 결과를 직접 적는다 |
| 커밋된 `node_modules` 정리 여부·시점 | `main`·`dev`·`frontend`·`frontend-v2`에 176개 파일이 추적되고 있어 규칙과 현재 상태가 어긋난다(2.5) | 이미 추적되는 파일을 개인이 임의로 정리하지 않는다 |
| GitHub 브랜치 보호 규칙 현황 | `main` 직접 Push가 기술적으로 막혀 있는지 확인 필요 | 규칙이 없다고 가정하고 스스로 지킨다 |
| `Kr-TeamWise` 조직·이전 저장소와의 관계 | 병합 이력과 권한 구조를 이해하는 데 필요하다 | 확인 전에는 추정하지 않는다 |

## 부록 A. 자주 쓰는 명령어

```bash
# 상태 확인
git fetch --prune origin
git status
git branch --show-current
git branch -a

# 브랜치 비교
git rev-list --left-right --count origin/A...origin/B   # 갈라진 커밋 수
git diff --name-status origin/A...origin/B              # 달라진 파일
git log origin/A..origin/B --oneline                    # B에만 있는 커밋
git merge-base origin/A origin/B                        # 공통 조상

# 브랜치 이동하지 않고 내용 확인
git ls-tree -r --name-only origin/<브랜치>
git show origin/<브랜치>:<파일경로>

# 같은 기능이 이미 있는지 확인 (작업 시작 전 필수)
git log --all --oneline --grep="<기능 키워드>"
git log --all --oneline -- "<관련 파일 경로>"
git grep -l "<필드명·함수명>" origin/<브랜치>

# 마이그레이션 번호 충돌 확인
git ls-tree -r --name-only origin/<브랜치> -- backend/<앱>/migrations

# 작업 브랜치 생성
git switch -c feature/<기능명> origin/<기준브랜치>

# 병합 여부 확인
git branch -r --merged origin/main
git branch -r --no-merged origin/main
```

## 부록 B. 이 문서의 관리 규칙

- 이 문서는 **현재 유효한 기준**만 담는다. 브랜치 구조·담당자·절차가 바뀌면 갱신하고, 변경 이유는 14장 결정 기록에 남긴다.
- 3.1·3.2 브랜치 현황과 13.2 진행 작업 표는 사실이 바뀔 때마다 갱신한다. 갱신할 때 확인 날짜를 함께 적는다.
- 이 문서에 적는 커밋 수·날짜·파일 수는 확인한 시점의 값이다. 인용하기 전에 명령으로 다시 확인한다(부록 A).
- 날짜별 작업 내용, 기능별 구현 상세, 개별 프로젝트의 점검 이력은 이 문서에 쓰지 않고 각 작업일지 문서에 기록한다.
- 과거 작업일지는 고치지 않는다. 이후 발견한 오류·정정은 새 날짜에 기록한다.
